以下位置使用了 `open()` 但无 `try/except` 保护:

| `loc/importer.py` | 94-127 | 5 个 CSV 文件读取 |

## 3. 日志与可观测性

### 3.1 全局使用 print() 而非 logging

整个项目所有输出使用 `print()` + 手动 `flush=True`，而非 Python 标准 `logging` 模块。

| 影响 | 说明 |
|------|------|
| 无法控制日志级别 | 没有 INFO/WARNING/ERROR 分级 |
| 无法重定向 | 作为库使用时 stdout 被污染 |
| 无结构化日志 | 无法对接日志收集系统 |
| 性能差 | 每次 print 后 `flush=True` 强制刷新缓冲区 |

### 3.2 进度输出不一致

- `brand/model.py`: 使用 `i//10000` 显示 "万" 行
- `loc/builder.py`: 使用 `i//10000` + `w` 后缀
- `eval.py`: 使用 `k//10000` + `w` 后缀 + "non-empty lines"

不同文件使用不同的进度格式，且 `w` (万) 是中文互联网用语，非中文读者会困惑。

## 5. 代码架构与依赖

### 5.1 反模式: sys.path.insert

```python
# run.py:7, eval.py:11
sys.path.insert(0, BASE)
```

这种运行时路径注入是脆弱的:
- 如果项目被 pip 安装，此行多余且可能引入导入冲突
- 如果工作目录变化，可能导致导入失败
- 违背 Python 打包最佳实践

**建议**: 使用 `pip install -e .` + `pyproject.toml` 或相对导入。

### 5.2 反模式: 方法内懒加载 import

```python
# loc/builder.py:55
from loc.importer import _split_admin

# loc/recognizer.py:394
from loc.importer import classify_suffix

# org/recognizer.py:44
from brand.model import BrandModel

# org/recognizer.py:85
from core.types import ADMIN_SUFFIX_MAP  # 但文件顶部已从 core.types 导入
```

将 import 放在方法体内虽然避免了循环导入，但:
- 隐藏了真实依赖关系
- 每次调用产生微小的性能开销
- 如果模块路径变化，错误延迟到运行时才发现

### 5.3 磁盘文件路径深度假设

```python
# org/recognizer.py:45-46
base = os.path.dirname(os.path.dirname(__file__))
dict_dir = os.path.join(base, "dicts")
```

这假设 `org/recognizer.py` 在项目根下恰好两级。如果文件被移动到其他深度，路径计算失效。

**建议**: 通过环境变量或配置文件指定路径，而非从 `__file__` 推断。

### 5.4 模块导入时的副作用

```python
# poi_dedup.py:15-25 (模块级代码)
AREA_SET = set()
for fname in ["areas.csv", "streets.csv", "villages.csv", "cities.csv"]:
    path = os.path.join(AREA_DIR, fname)
    if not os.path.exists(path): continue  # 静默跳过!
    with open(path, encoding="utf-8-sig") as f:
        for row in csv.DictReader(f):
            name = row.get("name", "").strip()
            if name: AREA_SET.add(name)
```

这段代码在 `import poi_dedup` 时执行，意味着:
- 即使不需要 AREA_SET(如测试)也会执行 I/O
- 文件缺失时静默构建不完整的集合
- 阻塞模块导入

## 6. Pickle 安全性

项目多处使用 `pickle.load`:

| 文件 | 说明 |
|------|------|
| `loc/builder.py:25, 192` | 加载/构建地名词典缓存 |
| `org/recognizer.py:78` | 加载 pruned 词典 |
| `brand/model.py:162` | 加载品牌模型 |

**风险**: pickle 反序列化可以执行任意代码。如果 .pkl 文件来自不可信来源或被篡改，存在远程代码执行风险。

**当前缓解**: 词典文件由训练 pipeline 生成，非外部输入。但风险应被文档化。

---

## 7. 多进程安全

工具脚本使用 `subprocess.Popen` 而非 `multiprocessing`，这在 macOS (spawn 模式) 下是正确的选择 (文档中也提到了这个坑)。

但存在两个问题:
1. 没有进程超时 — 挂起的 worker 导致整体 pipeline 永久卡住
2. 多个 chunk 可能同时写同一文件 (虽然当前设计避免了)
