# dict_ner 审计报告 — 交叉问题

> **审计版本**: v1.0  
> **审计日期**: 2026-07-06  

---

## 1. DRY 违反 (跨模块代码重复)

### 1.1 org ↔ poi 工具链重复 (~80%)

三对文件实现了几乎相同的逻辑，仅数据源和阈值不同:

| org 工具 | poi 工具 | 差异 |
|------|------|------|
| `tools/org_launch.py` (102行) | `tools/poi_launch.py` (124行) | poi 多了 dedup 步骤 |
| `tools/org_chunk_stats.py` (110行) | `tools/poi_chunk_stats.py` (147行) | poi 多了 T 源合并 |
| `tools/org_aggregate.py` (169行) | `tools/poi_aggregate.py` (145行) | poi 多了种子后缀注入 |

**影响**: 修改 pipeline 逻辑需同步修改两处，极易漏改产生 Bug。

**建议**: 抽取公共基类或 Pipeline 类，通过配置/子类化区分 org/poi 行为。

### 1.2 后缀发现+合并逻辑重复

`loc/importer.py:_split_admin` 与 `loc/recognizer.py:_generate_pattern_matches` 实现了几乎相同的算法:

1. 在文本中查找所有 ADMIN_SUFFIX_MAP 中的后缀
2. 按 end 位置排序
3. 合并重叠的后缀 (取较长的)
4. 生成 components/matches

**差异**: 排序键略有不同 (importer 用 `(end, -len(sfx))`; recognizer 用 `(end, -len(sfx), TYPE_PRIORITY)`)

**影响**: 修改合并算法需改两处；两处行为轻微不一致可能导致数据不一致。

**建议**: 提取为 `core/` 下的共享函数 `find_admin_boundaries(text) -> list`.

### 1.3 POI 后缀映射重复

`core/types.py:POI_SUFFIX_MAP` 与 `loc/importer.py:SUFFIX_TO_CATEGORY` 是同一概念的两份独立实现:

- `POI_SUFFIX_MAP`: 后缀→类别 (在 `core/types.py` 中, ~90 条)
- `SUFFIX_TO_CATEGORY`: 后缀→类别 (在 `loc/importer.py` 中, ~100 条)

**已观察到的差异**: `SUFFIX_TO_CATEGORY` 包含 `"医务室"`, `"卫生室"`, `"培训"`, `"教育"`, `"客栈"`, `"民宿"`, `"保险"`, `"证券"` 等条目，而 `POI_SUFFIX_MAP` 没有。

**影响**: 两个代码路径的 POI 分类结果不一致。`recognizer.py` 使用 `POI_SUFFIX_MAP` 优先，然后 fallback 到 `classify_suffix` (使用 `SUFFIX_TO_CATEGORY`)。

**建议**: 统一到一个数据源，作为外置配置文件(CSV/JSON/YAML)。

### 1.4 Bigram 提取逻辑重复

`brand/model.py` 中两个训练方法存在重复的 ngram 计数循环:

```python
# train_from_d222 (line 33-38)
for j in range(len(text)):
    self.unigram_counts[text[j]] += 1
for j in range(len(text) - 1):
    pair = text[j] + text[j + 1]
    self.bigram_counts[pair] += 1

# train_from_d2_csv (line 76-81) — 完全相同但加了 weight
for j in range(len(text)):
    self.unigram_counts[text[j]] += weight
for j in range(len(text) - 1):
    pair = text[j] + text[j + 1]
    self.bigram_counts[pair] += weight
```

**建议**: 提取 `_count_ngrams(text, weight=1)` 私有方法。

## 2. 错误处理缺失

### 2.1 文件 I/O 无错误处理

以下位置使用了 `open()` 但无 `try/except` 保护:

| 文件 | 位置 | 操作 |
|------|------|------|
| `loc/builder.py` | 25, 88, 108, 192 | pickle.load, csv 读取 |
| `loc/importer.py` | 94-127 | 5 个 CSV 文件读取 |
| `org/recognizer.py` | 78 | pickle.load |
| `brand/model.py` | 23, 50, 164 | csv 读取, pickle.load |
| `tools/org_sample_jsonl.py` | 20 | csv 读取 |
| `poi_dedup.py` | 15-25 | 4 个 CSV 文件在模块导入时读取 |

**影响**: 任何文件缺失/损坏都会产生不友好的 `FileNotFoundError`/`UnicodeDecodeError` 堆栈信息。

### 2.2 异常被吞

| 文件 | 行号 | 代码 | 被吞的错误类型 |
|------|:---:|------|------|
| `org/recognizer.py` | 195 | `except Exception: pass` | 所有 CSV 读取异常 |
| `tools/poi_launch.py` | 23-33 | `except:` (裸) | 所有异常，包括 MemoryError |
| `loc/builder.py` | 68 | `except ValueError: idf=1` | IDF 解析失败 |
| `tools/org_aggregate.py` | 36 | `except (ValueError, KeyError): pass` | 质量数据解析失败 |

### 2.3 子进程失败静默

`org_launch.py` 和 `poi_launch.py` 启动 16 个并行子进程，但使用 `Popen` 且仅打印 `returncode`，不中断 pipeline:

```python
# org_launch.py:65
proc = subprocess.Popen([...])
outs, errs = proc.communicate(timeout=3600)
print(f"  chunk {i:02d}: rc={proc.returncode}, {outs[-2:]}")  # 仅打印，不检查
```

而 `run_aggregate` 使用了 `check=True`:

```python
# org_launch.py:86
subprocess.run([..., AGGREGATE], check=True)  # 会抛异常
```

这种不一致意味着部分 chunk 可能失败但 aggregation 仍会执行。

## 3. 日志与可观测性

### 3.1 全局使用 print() 而非 logging

整个项目所有输出使用 `print()` + 手动 `flush=True`，而非 Python 标准 `logging` 模块。

| 影响 | 说明 |
|------|------|
| 无法控制日志级别 | 没有 INFO/WARNING/ERROR 分级 |
| 无法重定向 | 作为库使用时 stdout 被污染 |
| 无结构化日志 | 无法对接日志收集系统 |
| 性能差 | 每次 print 后 `flush=True` 强制刷新缓冲区 |

### 3.2 进度输出不一致

- `brand/model.py`: 使用 `i//10000` 显示 "万" 行
- `loc/builder.py`: 使用 `i//10000` + `w` 后缀
- `eval.py`: 使用 `k//10000` + `w` 后缀 + "non-empty lines"

不同文件使用不同的进度格式，且 `w` (万) 是中文互联网用语，非中文读者会困惑。

## 4. 硬编码与可配置性

### 4.1 数据字典硬编码在源码中

三大后缀字典全部写在 Python 源码中，无法由非开发人员修改:

| 字典 | 文件 | 条目数 | 说明 |
|------|------|:---:|------|
| `ADMIN_SUFFIX_MAP` | `core/types.py` | ~70 | 省/市/区/镇/村/路 后缀 |
| `LOCATION_SUFFIX_MAP` | `core/types.py` | ~100 | 方位/位置后缀 |
| `POI_SUFFIX_MAP` | `core/types.py` | ~90 | POI 后缀→类别映射 |

**建议**: 迁移到 CSV/JSON/YAML 配置文件。

### 4.2 魔法数字

项目中 50+ 处硬编码数字阈值无文档说明。典型例子:

| 文件 | 值 | 上下文 |
|------|:--:|------|
| `loc/builder.py` | 5, 3, 150000, 999999 | IDF 阈值、上限 |
| `loc/recognizer.py` | 0.0, 0.2, 0.3, 0.5, 1.0, 2.0, 5.0 | DP 转移代价 |
| `org/recognizer.py` | 50000, 0.8, 7.0 | 短词 d4 惩罚 |
| `brand/model.py` | 1, 0.3, 0.01, -10.0, 1e-12 | 平滑参数、默认分数 |
| `eval.py` | 5000, 1.5, 0.5 | 采样量、评分权重 |

### 4.3 共享常量重复定义

以下常量和路径在多个文件中独立定义:

| 常量 | 出现次数 | 涉及文件 |
|------|:---:|------|
| `NUM_CHUNKS = 16` | 4 | org_launch, poi_launch, org_aggregate, poi_aggregate |
| `VERSION = "v1.1.1"` 或等价 | 5+ | org_aggregate, poi_aggregate, org_launch, eval, pipeline |
| `ADDR_TYPES` 地址类型集合 | 3 | org_aggregate, poi_aggregate, org_chunk_stats |
| `COMPANY_SUFFIXES` | 2 | pipeline.py, poi_dedup.py |
| `CHINESE_CHAR` Unicode 范围 | 2 | org_chunk_stats, poi_chunk_stats |

**建议**: 创建 `core/config.py` 作为项目级配置单例。

## 5. 代码架构与依赖

### 5.1 反模式: sys.path.insert

```python
# run.py:7, eval.py:11
sys.path.insert(0, BASE)
```

这种运行时路径注入是脆弱的:
- 如果项目被 pip 安装，此行多余且可能引入导入冲突
- 如果工作目录变化，可能导致导入失败
- 违背 Python 打包最佳实践

**建议**: 使用 `pip install -e .` + `pyproject.toml` 或相对导入。

### 5.2 反模式: 方法内懒加载 import

```python
# loc/builder.py:55
from loc.importer import _split_admin

# loc/recognizer.py:394
from loc.importer import classify_suffix

# org/recognizer.py:44
from brand.model import BrandModel

# org/recognizer.py:85
from core.types import ADMIN_SUFFIX_MAP  # 但文件顶部已从 core.types 导入
```

将 import 放在方法体内虽然避免了循环导入，但:
- 隐藏了真实依赖关系
- 每次调用产生微小的性能开销
- 如果模块路径变化，错误延迟到运行时才发现

### 5.3 磁盘文件路径深度假设

```python
# org/recognizer.py:45-46
base = os.path.dirname(os.path.dirname(__file__))
dict_dir = os.path.join(base, "dicts")
```

这假设 `org/recognizer.py` 在项目根下恰好两级。如果文件被移动到其他深度，路径计算失效。

**建议**: 通过环境变量或配置文件指定路径，而非从 `__file__` 推断。

### 5.4 模块导入时的副作用

```python
# poi_dedup.py:15-25 (模块级代码)
AREA_SET = set()
for fname in ["areas.csv", "streets.csv", "villages.csv", "cities.csv"]:
    path = os.path.join(AREA_DIR, fname)
    if not os.path.exists(path): continue  # 静默跳过!
    with open(path, encoding="utf-8-sig") as f:
        for row in csv.DictReader(f):
            name = row.get("name", "").strip()
            if name: AREA_SET.add(name)
```

这段代码在 `import poi_dedup` 时执行，意味着:
- 即使不需要 AREA_SET(如测试)也会执行 I/O
- 文件缺失时静默构建不完整的集合
- 阻塞模块导入

## 6. Pickle 安全性

项目多处使用 `pickle.load`:

| 文件 | 说明 |
|------|------|
| `loc/builder.py:25, 192` | 加载/构建地名词典缓存 |
| `org/recognizer.py:78` | 加载 pruned 词典 |
| `brand/model.py:162` | 加载品牌模型 |

**风险**: pickle 反序列化可以执行任意代码。如果 .pkl 文件来自不可信来源或被篡改，存在远程代码执行风险。

**当前缓解**: 词典文件由训练 pipeline 生成，非外部输入。但风险应被文档化。

---

## 7. 多进程安全

工具脚本使用 `subprocess.Popen` 而非 `multiprocessing`，这在 macOS (spawn 模式) 下是正确的选择 (文档中也提到了这个坑)。

但存在两个问题:
1. 没有进程超时 — 挂起的 worker 导致整体 pipeline 永久卡住
2. 多个 chunk 可能同时写同一文件 (虽然当前设计避免了)
